A kill switch for agents: 546 ns a check, up to 76% fewer tokens

The question we started with was not about data centres. It was about fitness trackers and other light tech: how do you give a device with kilobytes to spare, no guaranteed network and no governance server the same runtime governance Axiom gives a fleet of agents? You need a stop that any component can pull and nothing can quietly undo. The answer we built is one small file and a check cheap enough to make before every step. We built it for our own agent runtimes first, where we could measure it, and this note reports what it costs and what a stop saves.

Where this came from

A fitness tracker, a smart ring or a sensor hub can't call a governance service before every action. It may be offline, it has a few hundred kilobytes, and its companion app, its cloud account and its own firmware all need to be able to say stop without negotiating with each other. That ruled out a policy server, a message bus and a per-step RPC. It left four requirements:

  • State any component can read and write with no server. A single small file.
  • A check cheap enough to run before every step. It costs nanoseconds and makes no network call.
  • Easy to pull, hard to release. Anyone may raise the level. Lowering it needs a signature.
  • Fail closed. A corrupt or tampered file means stop, not go.

This is a project we started in June, and it isn't competing with anyone. What inspired us to look back at it was Infinity, an Apache-2.0 research runtime that AWS released on 23 October 2026 as part of the Hydro project with UC Berkeley. It suspends agents while they wait on tools, so very many can run at once; our slim agent fabric takes the same approach. One of the open questions its authors publish is how a runtime should establish where events come from, so that actions stay traceable and accountable, without giving up a stateless architecture. That is the tracker problem at fleet scale: govern many actors with no central service holding the state. The kill switch is the first piece we built in answer, and the signed, hash-chained receipts are the start of the provenance half.

Our agent runtimes were the place to build and measure that shape first: thousands of agents on one machine, real model calls and real tokens. A tracker port is the next step, not this one (see the limits below).

The ladder

The same five levels our robot-fleet simulator already used, applied to agents. Scopes are fleet, loop:<name>, run:<id> and fabric:<name>; the highest one that applies wins.

LevelWhat happens
L1 WARNINGReceipts are flagged. Nothing else changes.
L2 THROTTLESide effects wait for a human, and one model call runs at a time.
L3 SUSPENDNo new model calls. Work checkpoints and resumes exactly once when released.
L4 TERMINATEIn-flight work is dropped or aborted, running commands are killed with their children, and runs end for good.

The state is .nodexloop/governance.json, here 404 bytes. A raise needs no key and can only go up. A release is a section HMAC-SHA256-signed with a release key; it is the only way down. A missing file reads as NORMAL; an unreadable file, or a release that does not verify, reads as L3. Every change appends a hash-chained receipt of about 205 bytes.

The portable part is the file format plus one HMAC-SHA256. The Python module is how we measured it, not what a tracker would run: most of its import time is pathlib, which firmware would not need.

The check costs less than a Python function call

The level is re-read at most once per poll interval (50 ms); between reads it is a clock compare and a dictionary lookup. Uncached reads show why the cache exists: on Windows, a stat alone costs tens of microseconds.

What a stop saves, and what it can't

1,000 agents, one task each (model → tool → model), 8 model slots, a simulated model: 20 ms prefill and 2 ms per output token, 128 output tokens per call. Unstopped, it spends 256,000 output tokens in 69.4 s. The stop lands about 25% of the way through.

L3 SUSPEND291.5341.548705

L4 saved 76% of the run's output tokens on average (70–79% across 10 trials). What still gets spent has two sources. The larger one is the decode tails of the 8 calls already on a model slot, which the Python fabric lets finish before dropping their replies. The smaller is a few calls that started after the raise: up to 6 out of 2,000 (mean 1.5 at L4, 0.8 at L3). They start in the window before the fleet's next 50 ms poll sees the change, and the window also includes the writer's own lock and write. That is the price of a check that costs nanoseconds instead of a stat: a shorter poll narrows the window, and the propagation table shows what it costs. After an L3 release, every task finished exactly once (yes in every trial).

A real model: drain versus abort

qwen2.5-coder:3b on Ollama (NVIDIA GeForce GTX 1660 Ti, 6144 MiB), 8 streamed calls of up to 256 tokens, one at a time. An L4 lands 30–45% of the way through. Drain lets the call in flight finish, as the Python fabric does today. Abort closes the stream, as the NodeXLoop extension does with its per-call AbortController.

What we're honest about

  • Nothing here ran on a tracker. Every number is from one 12-thread Windows desktop (Intel64 Family 6 Model 165 Stepping 2, GenuineIntel, 17.0 GB). The design is aimed at light devices; the measurement isn't from one yet. Testing on a Jetson Orin Nano Super is next, then a microcontroller port of the file reader in C.
  • The halt experiment's tokens are simulated (timed sleeps for prefill and decode). The live experiment is the one with real tokens, and it runs one call at a time against one Ollama slot.
  • The Python fabric drains, it doesn't abort. An L4 drops replies that land after the stop, but the tokens of a call already on a slot are spent. The live comparison shows what an abort-aware backend would save; building one is open work.
  • A raise isn't free for the writer. Locking, writing and receipting took 39 ms (p50) here. That's acceptable for a rare action, but it's measurable.
  • Not a security boundary against code running as the same user. Such code can read the release key. The guarantees are that a stop always works and a release is always deliberate and receipted.

The open problem

How small can the reader get? A firmware implementation needs a JSON reader, HMAC-SHA256 and a clock. We think that fits in a few kilobytes of flash, but we haven't measured it yet.
